# Phase 0 Research: AISAT-INTEL MVP (Phase 1)

**Date**: 2026-06-06 | **Plan**: [plan.md](./plan.md)

All Technical Context items are resolved; the spec carries no remaining `NEEDS CLARIFICATION` markers (five were resolved in the Clarifications session on 2026-06-05). This document records the load-bearing technical decisions, their rationale, and rejected alternatives.

## 1. Access-control enforcement (data layer, not prompt)

- **Decision**: Enforce isolation at two layers: PostgreSQL Row-Level Security (`workspace_id = current_setting('app.workspace_id')`) on every tenant-scoped table, and Qdrant payload pre-filters (`workspace_id` match + `access_level Range(lte=user_access_level)`) injected before every vector search. Clearance is a fixed ladder of 5 ordered levels (1–5); a document with no explicit level defaults to the uploader's own clearance.
- **Rationale**: SC-001 is a hard release blocker (100% correctness). Prompt-level instructions are bypassable by injection; data-layer filters are not. Two independent layers give defense in depth — RLS protects relational reads, payload filters protect vector reads.
- **Alternatives considered**: (a) Prompt-only scoping — rejected: trivially defeated and untestable. (b) One Qdrant collection per workspace — rejected: collection sprawl and cost; payload isolation with indexed fields scales better for Phase 1. (c) Application-layer filtering after retrieval — rejected: leaks restricted docs into process memory and risks accidental inclusion.

## 2. Cross-clearance semantic cache keying

- **Decision**: Cache key = `sha256(workspace_id | user_id | effective_access_level | model | normalize(query))`. Personal-knowledge answers cache per-user; workspace-only answers MAY cache per `(workspace_id, access_level)` via a `cacheable_scope` flag the retriever sets when no personal document contributed.
- **Rationale**: The same query string legitimately resolves to different documents per clearance, so a query-only key would leak a higher-clearance answer to a lower-clearance member (violates SC-001). Binding tenant + identity + clearance makes a cache hit reusable only within an identical authorization scope (Clarification Q2).
- **Alternatives considered**: (a) Query-only key — rejected: cross-clearance leak. (b) No caching — rejected: needlessly sacrifices latency/cost; safe caching is achievable. (c) Per-user only for everything — rejected: lower hit rate; workspace-only answers can safely share.

## 3. Credit accounting: Redis hot path + Postgres ledger

- **Decision**: Redis holds the authoritative hot balance (`DECRBY`, atomic); PostgreSQL `credit_ledger` (append-only, `idem_key UNIQUE`) is the durable source of truth, written async via a Redis outbox drained by the **Go kernel billing worker — the sole `credit_ledger` writer** (`backend-go/kernel/billing/`). Python spend producers (query/ingest/agent workers) compute cost and **publish** `billing.deduct.<ws>` events but never write the ledger or touch the Redis balance, keeping one authoritative money-writer behind the kernel and RLS. Every credit-affecting operation carries an idempotency key; a `SET NX billing:applied:{idem_key}` guard plus the ledger unique index make retries/double-clicks no-ops. Cold-start rehydration rebuilds the Redis balance from the ledger under a per-workspace lock; an hourly reconciliation cron corrects drift with `operation_type='reconcile'` rows. The outbox key space and the reconciliation scan are **partitioned by workspace shard** from day one: Phase 1 runs a single drainer + single hourly reconcile, but the shard key lets Phase 4 run N parallel drainers/reconcilers without redesigning the key space or risking double-apply (§14). The drainer and reconcile loops run in the dedicated `cmd/worker` role (external CronJob → NATS tick → queue-group consumer, idempotent atomic claims), never as in-process timers in the request-serving `cmd/api` tier (§15).
- **Rationale**: SC-006 demands exact accounting and no double-charge. Atomic Redis decrement gives sub-ms enforcement on the hot path; the durable ledger guarantees recoverability and auditability; idempotency closes the retry double-charge hole.
- **Alternatives considered**: (a) Postgres-only synchronous deduction — rejected: too slow on the hot path, lock contention. (b) Redis-only — rejected: not durable; a Redis loss is a billing incident. (c) Best-effort ledger write — rejected: drops under failure; the outbox makes deduction and ledger intent atomic.

## 4. Provider fallback strategy (one-hop)

- **Decision**: LLM aliases (`fast`, `smart`, `embed`, `rerank`) resolve to `{primary, fallback}` (plus multi-key/deployment load-balancing) in the **standalone LLM gateway** (LiteLLM router config, Bifrost-swappable — §21), **not** in application code. Fail over on timeout / 5xx / rate-limit only, capped at one hop, with an `llm.fallback.count` metric and a circuit breaker. `embed` has **no per-call fallback**: the `embed` alias is pinned single-model (no fallback route), and a down primary embedder parks the chunk in `ingestion.dlq` for retry rather than embedding with a different model.
- **Rationale**: Edge case + FR-029 require degradation, not outage, while never failing over on "low-quality" output (that is an eval concern). Embedding models cannot be mixed within one Qdrant collection without making distances meaningless, so per-call embed fallback would silently corrupt retrieval quality.
- **Alternatives considered**: (a) Multi-hop fallback — rejected: unbounded latency. (b) Quality-based fallback — rejected: undefined/abusable signal, not a reliability event. (c) Per-call embed fallback — rejected: index inconsistency.

## 6. Async agent execution over NATS (not in-process)

> **Stays here.** This is *this product\'s* decision (deployment/transport). For the runtime's transport-agnostic `Bus` port version see [intel-agent research](https://github.com/truongpx396/intel-agent/blob/main/specs/001-agent-runtime/research.md).

- **Decision**: The Go BFF publishes queries to `query.agent.<workspace_id>` and returns an SSE stream ID; a Python worker pool consumes via a **NATS JetStream durable pull consumer bound to a per-subject queue group** (not core NATS), runs the LangGraph RAG graph ([contracts/agent-graph.md](./contracts/agent-graph.md)), checkpoints state to Redis (AOF), and streams partial results via Redis pub/sub → Go SSE → browser. Only `intent=long_horizon` runs create a durable `agent_run` row; short interactive queries do not. The Go SSE relay is built behind a clean boundary (it only subscribes to Redis pub/sub by `stream_id` and forwards) so it is a **logically separable tier** from the request-handling BFF (see §14).
- **Rationale**: Decouples request latency from model latency, enables independent worker scaling per NATS subject via the queue group (KEDA on JetStream consumer lag in Phase 2), and survives worker restarts via JetStream redelivery + Redis checkpoints. Core NATS would lose in-flight messages on a worker crash and expose no lag metric to autoscale on; JetStream is therefore a Phase 1 lock-in (§14). Matches the streaming UX (SSE event taxonomy) and the durability needs of long-horizon tasks (SC-009).
- **Alternatives considered**: (a) In-process LangGraph per HTTP request — rejected: couples latency, no durability, poor scaling. (b) WebSockets — rejected: SSE is sufficient for server→client streaming and simpler behind CDN. (c) Core (non-JetStream) NATS — rejected: no persistence, no durable consumers, no consumer-lag signal — unfixable later without rewriting every publisher/consumer.
- **Why two transports (JetStream + Redis pub/sub), not one**: the two hops have opposite needs. Hop 1 (BFF→worker) is *durable work dispatch* — must survive a crash, be redeliverable, and expose consumer lag → JetStream. Hop 2 (worker→relay→browser) is *ephemeral live-token fan-out* to an already-connected client — lowest latency, simple per-`stream_id` fan-out, fire-and-forget → Redis pub/sub (already the streaming control plane: checkpoints, cache, credits). Using JetStream for hop 2 would add per-token persistence + per-query stream/consumer churn for a durability nobody needs (a lost *token* is cosmetic; credits/audit/final answer are authoritative in Postgres). Crash recovery already lives at the right layer: JetStream redelivers the *job*, the Redis checkpoint resumes the *run*, the relay just re-subscribes. If replay-on-reconnect is ever required, the upgrade is a **Redis Stream** (`XADD`/`XREAD`) per `stream_id` — same Redis, not JetStream.

## 8. Ingestion pipeline + upload boundary

- **Decision**: Browser uploads directly to S3 via presigned URL; an S3 event publishes to `ingestion.{mime}.{workspace_id}`; Python workers route by MIME (MarkItDown for PDF/DOCX/MD, GPT-4o-mini captioning for images; video/audio is a registered-but-501 stub). Web links are no longer a standalone ingestion path — they are crawled (Crawl4AI, via the shared `web_distill` capability) inside member-initiated note enrichment, and only the member-accepted note body is ingested (FR-001). BAML extracts advisory metadata (tags/data_type/summary/suggested_sensitivity); security fields are stamped server-side. A per-file size limit (admin-configurable per workspace, default 50 MB) is enforced at the upload boundary before any ingestion or spend.
- **Rationale**: Direct-to-S3 keeps large payloads off the app servers; MIME routing matches FR-001/FR-002/FR-003; the size limit (Clarification Q4) bounds cost and processing time and gives a clear oversize rejection rather than silent failure.
- **Alternatives considered**: (a) Proxying uploads through the BFF — rejected: memory/bandwidth pressure. (b) Model-inferred access level — rejected: a malicious upload could self-tag permissive (FR-004/FR-005).

## 9. PII scrubbing & retention window

- **Decision**: A PII filter runs in the gateway **before** any prompt/response is written to a trace or eval store. Raw prompt/response bodies are retained for a **30-day** window, after which they are purged (partition `DROP`) and only metadata, hashes, and aggregates remain. `llm_call_log` and `agent_audit_log` never store raw message bodies — only metadata, token counts, and hashes.
- **Rationale**: FR-024 + Clarification Q5 fix the window at 30 days. Scrub-before-write minimizes PII exposure; partition-drop expiry is cheap and tombstone-free. (Note: the source draft mentioned a 7-day Langfuse window; the clarified spec value of 30 days is authoritative and supersedes it.)
- **Alternatives considered**: (a) Indefinite raw retention — rejected: privacy/compliance risk. (b) Scrub-after-store — rejected: raw PII briefly persists. (c) Row-delete expiry — rejected: expensive, leaves tombstones.

## 10. Redis role separation (single cluster, logical split)

- **Decision**: Phase 1 runs one Redis cluster but separates roles by logical DB + key-prefix: durable state (credit balance, idempotency keys, `agent_run` checkpoints) runs `noeviction` + AOF; ephemeral cache (semantic/exact cache, hot-index flags) runs `allkeys-lru`, AOF off; counters (rate limits, daily budgets) run `volatile-ttl`. Pub/Sub for SSE fan-out is transient.
- **Rationale**: These roles have incompatible durability/eviction profiles — an LRU policy correct for the cache would silently evict credit balances or in-flight checkpoints (a billing/data incident). Logical separation makes the Phase 2 split into independent clusters a config change, not a refactor.
- **Behavior under Cluster / failover** (why scaling Redis is safe): a `SET NX` lock is **not** a correctness primitive under async-replication failover — a primary can ACK the lock, die before replicating, and a promoted replica grant it twice (the standard Redlock critique). The design never relies on it: every Redis guard has a Postgres backstop (`credit_ledger.idem_key UNIQUE`, notifications `(user_id, idem_key) UNIQUE`, the janitor's conditional `UPDATE … WHERE status='running'` fencing claim — §15), so a two-leader failover window produces zero duplicate effects. Four residual *scale* (not correctness) requirements when moving to Redis Cluster: (a) **hash-tag a workspace's keys** (`credit:{ws}:balance`, `billing:applied:{ws}:{idem}`) so they colocate on one slot and stay atomically scriptable across slots; (b) the hot `DECRBY` balance is a **cache** — a lost decrement on failover is a temporary-overspend/RPO question corrected by the hourly reconcile, never a double-charge; (c) rate-limit/budget counters **and** the opaque session store are Redis-only and **fail-safe** (a failover lets a few extra ops through / logs users out — best-effort, not a money or security hole); (d) **SSE fan-out pub/sub does not survive naive Cluster mode** — plain `PUBLISH`/`SUBSCRIBE` is broadcast across the *entire* cluster bus to every node, so the streaming hop ([sse-events.md](./contracts/sse-events.md)) must move to **sharded pub/sub** (`SPUBLISH`/`SSUBSCRIBE`, Redis 7+) keyed by a **slot-hash-tagged `stream_id`** (`{stream}:<id>`) so a token reaches only the relay replicas on that shard. Because any relay replica already serves any `stream_id` with no sticky sessions (§14), this is a keying change, not a topology change — but it is the same decision as the SSE-relay split, so the two are one workstream ([phase-4 items 2 + 6](../draft-plan.md#6-redis-high-availability)), not two phases. Verifying reconciliation + rehydration across failover is [phase-4 item 6](../draft-plan.md#6-redis-high-availability).
- **Alternatives considered**: One Redis with a single eviction policy — rejected: cache pressure would evict durable state.

## 11. Local agents (optional, additive)

- **Decision**: Local agents are optional; all core features work with zero agents (SC-008). A registered device gets a scoped, revocable PAT (user + workspace). Default `proxy` sub-mode routes LLM calls through `/llm/proxy` (metered, moderated, audited); `byok` sub-mode bypasses server LLM metering/moderation but still routes MCP tool calls server-side and is disableable per workspace by an admin. - **Rationale**: FR-025–FR-028 + SC-008/SC-009. Optionality keeps the core product independent of agents; the proxy default preserves metering/audit; BYOK is an explicit, admin-gateable trade-off.

## 14. Scale-forward seams locked in Phase 1 (rework-risk decisions)

These five decisions are fixed in Phase 1 not because Phase 1 needs the scale, but because deferring them past implementation turns an additive Phase 4 change into a rewrite. They cost nothing now and preserve the option to scale later. Provisioning the scale itself — KEDA, PgBouncer, Redis/Qdrant HA, load tests — remains Phase 4 ([draft-plan.md — Phase 4](../draft-plan.md#phase-4-scalability-and-resilience-hardening)).

- **NATS = JetStream, durable pull consumers, per-subject queue groups (not core NATS).** Crash recovery, DLQ redelivery, and autoscale-on-consumer-lag all assume persistent streams + durable consumers. Core NATS would lose in-flight messages on a worker crash and leave no lag metric to scale on — unfixable without rewriting every publisher/consumer. Queue groups make adding pods pure horizontal scale-out. (§6, [contracts/nats-subjects.md](./contracts/nats-subjects.md))
- **The SSE/edge relay is a logically separable tier from the request-handling BFF.** REST aggregation (CPU-bound, short-lived) and SSE termination (connection-bound, long-lived) have opposite scaling profiles. Packaged like the Python tier (one image, role-selected at deploy): the Go BFF is a **single image with two entrypoints** — `cmd/api/main.go` (REST) and `cmd/relay/main.go` (streaming) — sharing all `internal/` code, auth, the Redis pub/sub client, and the SSE event contract, so the `stream_id` producer (`POST /query`) and consumer (`GET /query/{streamId}`) can never version-skew. Phase 1 MAY co-deploy them in one process; Phase 4 deploys `api` and `sse-relay` as independently-scaled services. Stream *creation* (`POST`) is an `api` concern; only the long-lived `GET` belongs to the relay. Because the relay subscribes to Redis pub/sub keyed by `stream_id` (not in-process worker output), **any relay replica can serve any stream — no sticky sessions** — making it trivially horizontally scalable. (§6, [contracts/sse-events.md](./contracts/sse-events.md))
- **The Redis credit outbox key space is workspace-partitionable from day one.** Phase 1 runs a single billing-worker drainer + single hourly reconciliation, but outbox keys and the reconcile scan are sharded by workspace so Phase 4 can run N parallel drainers/reconcilers by shard without redesigning the key space or risking double-apply. (§3)
- **Qdrant stays payload-isolated within shared `personal`/`workspace` collections, with a documented re-shard/replication trigger.** The shared-collection + payload-filter choice (§1) is compatible with Qdrant's within-collection sharding and replication (additive). The watch-item is collection size: a re-shard / cluster-replication decision is triggered when the `workspace` collection approaches its node memory/latency budget — flagged now as a planned threshold, not an incident. (§1)
- **Scheduled & background work runs single-owner in a dedicated `cmd/worker` role, never inside a request-serving tier.** Periodic jobs (outbox drain, hourly reconcile, stale-heartbeat janitor, DLQ sweeps, `llm_cost_daily` matview refresh) are triggered by an external CronJob → NATS tick → JetStream queue-group consumer, and every action is an idempotent atomic claim — so adding `api`/`relay`/`worker` replicas can never double-fire a timer. Embedding these loops in `cmd/api` now would make Phase 4 autoscaling silently multiply them (N concurrent reconcilers/janitors); extracting them later means re-homing every job. (§15)

## 15. Scheduled & background work — single-owner execution (no duplicate timers)

- **Decision**: No scheduled or background loop runs inside a request-serving tier. All periodic/background work — credit-outbox drain, hourly reconciliation, `agent_run` stale-heartbeat janitor, DLQ retry sweeps, and the `llm_cost_daily` matview refresh — runs in a dedicated **`cmd/worker` role** (same Go image as `cmd/api`/`cmd/relay`, role-selected at deploy; §14), with the Python stale-heartbeat janitor likewise deployed as its own single-owner role rather than a loop inside every `long_horizon` pod. Scheduling is **external and event-driven** — a pluggable scheduler (Kubernetes `CronJob`, DigitalOcean App Platform scheduled component / Function, or a plain `cron`/systemd timer on a Droplet; locally a Make target or a single in-process ticker in the one `worker`) emits a NATS JetStream tick (`billing.reconcile.tick`, `agent.janitor.tick`, `usage.matview.refresh`). The “no in-process `time.Ticker`” rule applies to the **request-serving tiers** (`api`/`relay`); the single-owner `worker` MAY use an internal ticker, since correctness rests on the atomic claim below, not on the trigger. Each tick / outbox / DLQ subject is consumed by a **durable queue group → exactly one worker handles each event**, with JetStream redelivery on crash. Correctness never depends on “only one replica is running”: every scheduled action is an **idempotent atomic claim**, so a duplicate delivery is a no-op — the janitor re-queues only via a conditional transition (`UPDATE agent_run SET status='queued' WHERE id=$1 AND status='running' AND last_heartbeat_at < $2 RETURNING id`), reconcile guards each hour-bucket with `SET NX reconcile:lock:{shard}:{hour_bucket}`, and the outbox uses an atomic pop (`LPOP` / Stream consumer-group) plus `credit_ledger.idem_key UNIQUE`. The matview refresh uses `REFRESH MATERIALIZED VIEW CONCURRENTLY` (requires a UNIQUE index) so a duplicate tick is at worst redundant work, never a lock error.
- **Rationale**: Background loops embedded in the `api` tier multiply with replicas (2 today, autoscaled in Phase 4), so a “single hourly reconcile” silently becomes N concurrent reconcilers — racing `reconcile` deltas (SC-006), triple-re-queued agent runs and triple spend (SC-009), and colliding `REFRESH MATERIALIZED VIEW`. Separating *who schedules* (CronJob), *who executes* (queue-group worker), and *what guarantees correctness* (atomic claim + data-layer idempotency) makes the common path need **no leader election**, and keeps Phase 4 horizontal scaling purely additive (more workers = more throughput; the §3 shard keys keep ownership clean). Leases and queue groups are throughput optimizations; the data-layer idempotency is the **only** correctness guarantee — so a transient two-leader window (deploy overlap, network partition, lease handoff) still produces zero duplicate effects.
- **Alternatives considered**: (a) In-process `time.Ticker` in `cmd/api` guarded by a Redis leader lease — rejected: a lease held by a crashed pod, or handoff during a rolling deploy, transiently yields two leaders, and correctness would rest on that weakest link. (b) A durable-execution engine (Temporal / River / Asynq) — rejected for Phase 1: JetStream redelivery + Redis checkpoints + atomic claims already give durable, exactly-once-*effect* execution; a workflow engine is a Phase 4+ “if long-horizon orchestration outgrows LangGraph” decision, not an MVP dependency. (c) Postgres `pg_try_advisory_lock` as the primary guard — kept as the **optional HA gate** for any residual in-process loop (auto-released on connection drop, unlike a TTL lease) or the k8s `Lease` API, but not the primary mechanism, which stays the external trigger + idempotent claim.

## 16. Chunking strategy — structure-aware + parent/child + contextual retrieval

- **Decision**: Three layered techniques in `services/ingestion/chunker.py`. (1) **Structure-aware splitting** — split on document structure (markdown headings, paragraph/sentence boundaries, table rows, code fences) rather than a fixed character window, so a chunk never straddles a heading or cuts mid-sentence; fall back to a recursive token splitter only for unstructured text. (2) **Parent/child ("small-to-big")** — the *child* chunk (~200 tokens) is what gets embedded and searched (precise match); on a hit, retrieval expands to its *parent* (~1000 tokens, linked by `parent_doc_id`) before sending to the LLM (complete context for grounded citation). (3) **Contextual retrieval** (Anthropic-style) — before embedding, each child chunk is prefixed with a short LLM-generated situating line ("This excerpt is from *<doc title>*, section *<…>*; it discusses *<…>*") produced via the `fast` alias, with the per-document summary computed **once** and reused across that document's chunks to bound cost. The prefix is embedded *with* the child (lifting recall on pronoun-/acronym-/context-poor fragments) but is **not** a citation span. The contextual-prefix step is **flag-gated** (kernel `Flags`, `chunking.contextual_prefix`), defaults on for text documents, and must clear the `evals/run.py` recall/MRR/citation gate before it is enabled in CI.
- **Rationale**: Naive fixed-window chunking is the single biggest avoidable recall loss in production RAG — context-poor fragments embed ambiguously, and a mid-sentence cut corrupts both the retrieval unit and the cited span (SC-002/SC-003). Structure-aware boundaries + small-to-big is the standard answer: a *precise* retrieval unit plus a *complete* generation unit. Contextual retrieval is a measured, high-ROI recall win (Anthropic reports a large drop in retrieval-failure rate from per-chunk situating context) that fits cleanly here because the `fast` alias + per-doc summary reuse keep the added ingestion cost bounded and the gateway already meters/traces it. Gating it behind a flag + the eval gate keeps citation fidelity a *verified* property, not an assumption.
- **Alternatives considered**: (a) Fixed-size character windows with overlap — rejected: ambiguous embeddings and broken citation spans. (b) Semantic chunking (embedding-distance boundary detection) — deferred: higher ingestion cost and tuning burden for marginal gain over structure-aware boundaries on the target corpora; revisit only if eval recall stalls. (c) Embedding the contextual prefix as a *separate* vector — rejected: doubles index size and splits a chunk's signal across two points; prefix-then-embed keeps one vector per child.

## 18. Dead-letter drain & poison-message handling — bounded re-drive, then terminal park

- **Decision**: Every DLQ subject (`ingestion.dlq.<ws>`, `notify.email.dlq.<ws>`, and any future `*.dlq.<ws>`) is drained by a single **generic DLQ sweeper** that runs single-owner in `cmd/worker`, triggered by an external `dlq.sweep.tick` (the same pluggable scheduler seam as §15) and consumed by a durable queue group → exactly one worker per tick. Each parked message carries a `dlq_attempts` counter and a `first_failed_at`. For each message the sweeper either (a) **re-drives** it — if `dlq_attempts < MAX_DLQ_ATTEMPTS` (default 5) and an exponential-backoff window keyed on `first_failed_at` has elapsed, it re-publishes the message to its **original work subject** (the embed step for `ingestion.dlq`, `notify.email.<ws>` for the email DLQ) with `dlq_attempts+1`, so the **owning tier reprocesses it** (Python re-embeds with the *original* model only, §4; the Go email worker re-sends) — or (b) **terminally parks** it — once `dlq_attempts ≥ MAX_DLQ_ATTEMPTS`, it writes the message to a durable `dead_letters` Postgres table (queryable by admins for inspection / manual replay) and emits a `dlq.dead.count` metric for alerting; the message is never re-driven again.
- **Why re-drive to the live subject, not reprocess inside the sweeper**: the sweeper is a generic Go mover that knows nothing about embedding or SMTP. Re-publishing to the original subject keeps the actual retry in the tier that owns it (Python embed / Go mailer) and reuses that worker's existing idempotency — chunk identity for embeds, and the email worker's "mark sent only after provider-accept" rule — so a re-drive of a genuinely-unsent item delivers exactly once while a duplicate is a no-op. Same separation as §15: *who schedules* (cron tick) vs *who executes* (owning worker) vs *what guarantees correctness* (data-layer idempotency).
- **Why a hard attempt cap**: without a terminal state a poison message (malformed payload, permanently-rejecting recipient) loops forever, burning provider calls and masking the failure. `MAX_DLQ_ATTEMPTS` + the `dead_letters` table converts an unbounded retry into a bounded, observable, replay-on-demand outcome — "never dropped" becomes "either recovered or visibly dead," not "retried indefinitely." For email specifically, hard bounces/complaints short-circuit even earlier via `email_suppressions` (US8), so the cap mainly catches transient-looking-but-permanent failures.
- **Alternatives considered**: (a) JetStream `MaxDeliver` + a native DLQ only (no sweeper) — rejected: gives in-stream redelivery but no *cross-outage* re-drive (a message parked after `MaxDeliver` just sits), no backoff control, and no queryable terminal store. (b) Per-pipeline bespoke retry loops — rejected: duplicates backoff/cap/poison logic in every worker and re-tier-couples the sweeper. (c) Infinite re-drive with alert-only — rejected: a poison message loops forever and the alert never clears.

## 19. Policy authority vs enforcement points (one policy, many PEPs)

> **Stays here.** This is *this product\'s* decision (deployment/transport). For the runtime's `Policy` port version see [intel-agent research](https://github.com/truongpx396/intel-agent/blob/main/specs/001-agent-runtime/research.md).

- **Decision**: Enforcement is **distributed by necessity but derives from a single policy authority** — a policy-decision/policy-enforcement (PDP/PEP) split. Each rule has **exactly one authoritative source**, read by every tier that enforces it; no tier keeps a second hand-maintained copy. The Go kernel is the **owner/author** of policy (it issues device PATs, writes `agent_policies`, defines budgets and rate limits); the Python tiers and the data layer are **enforcers** that read that authority.
  - **Tool ACL** → `agent_policies.allowed_tools` (Postgres). Enforced at *both* the Go policy chain (ingress for `/query`, `/llm/proxy`) and the Python MCP dispatch guard — both read the same row; neither hardcodes a tool list.
  - **Clearance / tenancy** → the RLS predicate (migrations) + the clearance ladder. The Go tenant middleware **and** the Python tool/retrieval tier both set the same `app.workspace_id` / `app.user_id` / `app.clearance` GUCs from the PAT/Actor; Postgres RLS + the Qdrant payload filter are the actual enforcement (§1).
  - **PAT validity / revocation** → one Redis PAT/session store. Both `/llm/proxy` (Go) and the MCP server (`:8002`, Python) validate against it, so a revoked device dies at both entry points.
  - **Rate limit / abuse & body-size** → one set of Redis counters + limits, enforced at every client-facing ingress — the Go middleware **and** the direct MCP endpoint (which bypasses the Go chain, so it must apply the same policy itself; parity rule pinned in [contracts/mcp-tools.md](./contracts/mcp-tools.md)). A coarse per-IP/PAT limit MAY also sit at the edge (Caddy) covering both routes.
  - **Budget / metering** → Redis balance + `agent_policies.token_budget_day`. The budget *gate* runs at each call site (Go `/llm/proxy` for external agents; the Python gateway-client for ingest/agent); **cost is computed from the standalone gateway's returned token usage** and published as `billing.deduct.<ws>`; the **Go kernel billing worker is the single ledger writer** (§3, §21, SC-006). The standalone gateway's own budget/spend features are **disabled** — never a second money system.
- **Rationale**: Full centralization of the *enforcement point* into Go is neither possible nor desirable. (a) The strongest guarantees — RLS and the retrieval pre-filter — are **data-layer PEPs** that must run where the query executes (Python/Postgres/Qdrant): a GUC cannot be set on a connection Go does not hold, and security-trimming must happen *inside* the vector search (the same reason Phase 2 rejects an external policy engine — see draft-plan Access model). (b) The built-in LangGraph agent calls MCP tools **in-process** many times per query; forcing a Go round-trip per tool call would cripple the hot path. (c) Independent data-layer enforcement is defense-in-depth — even a bypassed upstream gate cannot leak, because Postgres/Qdrant refuse on their own. So the failure mode to prevent is **not** "more than one enforcer" (that is intended) but "more than one *definition*" — duplicated policy logic that drifts. One authoritative store per rule, read by all enforcers, removes the drift while keeping enforcement everywhere the data path requires it.
- **Alternatives considered**: (a) A single Go PEP, routing external MCP through Go — rejected: forces Go into a stateful MCP-protocol proxy, re-introduces the hot-path round-trip for shared logic, and relocates data-layer enforcement it cannot actually perform. (b) A synchronous external policy engine (OPA/Cedar/Zanzibar-style PDP) that both tiers call per decision — rejected for Phase 1: adds a network hop on the per-tool hot path; `agent_policies` is a small, role-keyed, cacheable table, so a shared *store* with local caching beats a remote PDP for this workload (revisit only if policy grows past role→allowlist/budget). (c) Status quo with each tier hardcoding its own allowlist/limits — rejected: two definitions drift and a security review cannot point to one source of truth.

## 20. Go↔Python LLM-proxy transport (synchronous streaming pass-through)

- **Decision**: The `/llm/proxy` hop from the Go BFF (`:8080`) to the **standalone LLM gateway** (`:4000`, LiteLLM — §21) is a **plain HTTP streaming pass-through** — **not** gRPC and **not** NATS. After the Go policy chain (PAT auth, `allowed_tools`/token-budget gate, credit deduct), the handler forwards the OpenAI-shaped request to the gateway's OpenAI-compatible endpoint (`POST http://llm-gateway:4000/v1/chat/completions`) over HTTP/1.1. For `stream:true` it relays the upstream response **verbatim as SSE** (`text/event-stream`), flush-per-chunk, holding no buffer; a non-stream call is a single request/response. **Cancellation is context-chained**: client disconnect cancels the Go handler's `request.Context()` → cancels the forwarded HTTP request → cancels the gateway stream → cancels the provider SDK stream (no server-side generation after the client is gone; partial tokens still settle — see [llm-gateway.md](./contracts/llm-gateway.md) "Cost settlement & stream cancellation"). The Python tier calls the **same** gateway (`:4000`) directly for its own ingest/agent LLM needs. With the standalone gateway, `/llm/proxy` is a Go→gateway call, so **there is no synchronous Go→Python call** in Phase 1 — every Go↔Python interaction is async over NATS JetStream (§6, §14).
- **Rationale**: (a) The external contract is **OpenAI-wire (HTTP + SSE)** — the whole point is "point `LLM_BASE_URL` here, no code change." Keeping HTTP+SSE end-to-end makes Go a thin reverse-proxy that never re-serializes the payload: the token frames the provider emits are the frames the client receives. gRPC in the middle would force an OpenAI-JSON ↔ protobuf ↔ SSE translation on **both** edges of the hop, for a stream that is just text tokens — a `.proto` to version and CPU per token, for no functional gain. (b) gRPC's real wins — typed schema, HTTP/2 multiplexing, first-class backpressure — pay off for **high-fan-out internal RPC**, and that class of Go↔Python traffic already runs over NATS JetStream. `/llm/proxy` is the lone *synchronous, long-lived, client-cancellable stream*, where HTTP streaming + context cancellation is the natural fit and a durable queue is the wrong tool. (c) It stays off NATS because it is a **request the external caller blocks on with a live back-channel**; the query path uses NATS + Redis pub/sub precisely because it is fire-and-forget with a *decoupled* SSE relay — the proxy has no decoupling need (the agent holds the connection, and a dropped partial is cosmetic, not billable truth).
- **Alternatives considered**: (a) **gRPC server-streaming Go↔gateway** — rejected for Phase 1: needs OpenAI-JSON↔protobuf↔SSE translation at the Go edge on every call plus a versioned `.proto`, for a text-token stream HTTP already carries losslessly, and it also breaks the OpenAI-wire swappability between LiteLLM and Bifrost (§21). (b) **NATS request-reply for the proxy** — rejected: at-least-once/fire-and-forget semantics and request-scoped, client-driven mid-flight cancellation map poorly onto JetStream, whose durability is wasted on cosmetic partial tokens. (c) **Go/Python calls providers directly (skip the gateway)** — rejected: duplicates alias resolution, multi-key LB, and one-hop fallback that the standalone gateway centralizes, scatters provider keys across every runtime, and breaks the single-chokepoint invariant (§21, constitution III).

## 21. LLM gateway: standalone, swappable service (LiteLLM → Bifrost), not a hand-rolled provider chokepoint

> **Stays here.** This is *this product\'s* decision (deployment/transport). For the runtime's thin `LLMGatewayClient` version see [intel-agent research](https://github.com/truongpx396/intel-agent/blob/main/specs/001-agent-runtime/research.md).

- **Decision**: The LLM gateway is a **standalone, OpenAI-wire-compatible service** — **LiteLLM** in Phase 1, **swappable with Bifrost** (Go-native) or Portkey by config with no caller changes — deployed on its **own port (`:4000`)** and holding **all provider API keys**. It is the single place model IDs, provider routing, and keys exist, and it owns the **commodity plumbing**: alias→model mapping (`fast`/`smart`/`embed`/`rerank`), **multi-key/deployment load-balancing**, one-hop provider fallback + circuit breaker (§4), retries/backoff, streaming, and token counting. Both runtimes call it as an OpenAI endpoint and never import a provider SDK:
  - **Python** `services/llm_gateway.py` is now a **thin gateway-client / policy wrapper** (not the provider chokepoint). Around each call it still owns the app-specific concerns the service cannot: the **clearance-scoped semantic-cache check** (before the call), **PII scrub**, **idempotency**, **cost computation → `billing.deduct.<ws>`**, and the Langfuse/`llm_call_log` annotation. It targets `LLM_GATEWAY_URL` (`:4000`).
  - **Go** `/llm/proxy` runs the policy chain (PAT auth, budget gate, **credit deduct**) then forwards straight to `:4000` — the external-agent path no longer detours through the Python tier (§20).
- **Two release-blocking invariants are preserved by keeping them *out* of the gateway**:
  - **Single ledger writer stays Go (SC-006).** The gateway is used for the call + returned token usage only; its own budget/spend/key-management features are **disabled**. Cost is computed at the call site and the ledger is written **only** by the Go kernel billing worker via `billing.deduct.<ws>`. Spend is emitted **per-caller from returned usage — gateway-agnostic, never a gateway-native callback** — so the LiteLLM↔Bifrost swap never touches the money path.
  - **Clearance-scoped answer-cache stays in the app (SC-001).** The gateway's built-in cache keys on prompt+model and is **off**; the semantic answer-cache lives in the Python query/agent path keyed by `workspace + clearance + authorized-doc-set`. Turning the gateway cache on would serve a higher-clearance answer to a lower-clearance member.
- **PII scrub** wraps the gateway's trace emission — the gateway's own tracer/body-logging is **off**, so the app client wrapper is the sole writer of prompt/response bodies (post-scrub) and the FR-024 scrub + 30-day-retention path cannot be bypassed.
- **Swappability contract**: `LLM_GATEWAY_KIND` (`litellm`|`bifrost`) + `LLM_GATEWAY_URL`, plus a gateway config file (`deploy/llm-gateway/*.yaml`) holding aliases/keys/LB routing. Because both engines are OpenAI-wire, **callers are unchanged** across the swap.
- **Tier-0 infra**: the gateway is on the critical path and custodies provider keys — HA, secret custody, and scaling (autoscale on in-flight; multi-key LB is now native) are **Phase 4** ([draft-plan.md — Phase 4](../draft-plan.md#phase-4-scalability-and-resilience-hardening)).
- **Provider-capacity math carries a per-query call-amplification factor.** Because "scalability is a provider-capacity problem" (below), the number that matters is not the *query* rate but the *provider-call* rate — and one interactive query fans out to **≈4–5 gateway calls** (`route` + `rewrite` + `rerank` + `generate`, semantic path — [contracts/agent-graph.md](./contracts/agent-graph.md)), plus per-chunk `embed` on ingest. So thousands of query/s ≈ **4–5×** that in provider calls/s. Every key-pool-sizing, provider-quota, rate-limit, and `$/QPS` estimate multiplies the query rate by this factor **before** comparing against provider limits; the gateway's multi-key LB scales throughput, but the quota it balances across is sized against the amplified rate. This is what makes the AI path **provider-quota- and cost-bound rather than compute-bound**, and it is a required input to the [phase-4 load/SLO plan](../draft-plan.md#9-load--soak-testing-harness).
- **Rationale**: For a gateway fronting third-party LLM APIs, scalability is a **provider-capacity** problem, not a compute one; the highest-leverage lever — **multi-key/deployment load-balancing** — is exactly what mature LLM gateways (LiteLLM, Portkey, Bifrost, Cloudflare/Kong AI Gateway) already solve, and is real, error-prone work to build well. So delegate the commodity plumbing to a proven, swappable service and keep custom **only** the security/billing invariants no gateway models the same way (SC-001 clearance-cache, SC-006 single-writer). A standalone *service* (vs. a library) is chosen for the stated scalability goal: it is language-agnostic (Go + Python call one endpoint) and independently scalable/operable.
- **Alternatives considered**: (a) **Hand-rolled Python provider chokepoint** (the earlier design) — rejected: reinvents provider LB/fallback/retries and, critically, multi-key load-balancing, which is the actual scale lever. (b) **LiteLLM as an in-Python *library*** — viable and simpler for Phase 1, but rejected as the target because it couples the gateway to one runtime and cannot be scaled/operated independently; the interface (`chat`/`chat_stream`/`embed`) is identical, so a team wanting less infra MAY start library-mode and swap to the service later with no caller changes. (c) **Trusting the gateway's own budget + cache** — rejected: a second money-writer breaks SC-006 and a prompt+model cache breaks SC-001. (d) **A gateway that is not OpenAI-wire / not swappable** — rejected: locks the design to one vendor and breaks the LiteLLM↔Bifrost swap. (e) **Gateway-native spend callback** (e.g. a LiteLLM callback publishing `billing.deduct`) — rejected: couples metering to one gateway's plugin API and breaks the Bifrost swap; per-caller emission from the returned token usage stays gateway-agnostic.

## 23. Notification fan-out durability — transactional outbox (crash-safe multi-channel delivery)

- **Decision**: The notification service does **not** deliver channels inline. On a `notify.<ws>` event it resolves preferences and, in **one Postgres transaction**, writes the `notifications` row **and one `notification_outbox` row per enabled channel** (`UNIQUE(notification_id, channel)`), then acks. A separate **Dispatcher** (queue-group consumer in `cmd/worker`) drains `notification_outbox` **at-least-once**, delivering each entry through its channel (in-app → Redis pub/sub `notify:user:<id>`; email → `notify.email.<ws>` → `kernel/mailer.go`), marking `delivered_at` or bumping `attempts` under backoff and parking in `dead_letters` after `MAX_DLQ_ATTEMPTS` (§18). The Redis `SET NX notify:applied:{idem_key}` guard is a **fast pre-check on the durable write only** — never on delivery. Correctness rests on `notifications.(user_id, idem_key) UNIQUE` + per-channel outbox uniqueness, not on the ephemeral Redis guard.
- **Why the inline design is unsafe**: the naive handler does `INSERT` + in-app publish + email enqueue as three **non-transactional** side-effects, gated by a `SET NX` that short-circuits the *entire* handler on a duplicate. If a replica sets the guard, commits the row, then crashes *before* the email enqueue, the JetStream redelivery hits the guard and skips — the email is **silently lost**, violating SC-013 ("one email") and FR-035 ("parked … rather than dropping silently"). The outbox makes the durable row and the delivery intents commit **together**, so recovery always has a queued intent to drive.
- **Why this mirrors billing (§3)**: the same two-store problem — a state change must touch Postgres *and* an external side-effect that cannot share the DB transaction. Billing solved it with the Redis `DECRBY + LPUSH` outbox + single-owner drain; notifications solve it with a Postgres transactional outbox + Dispatcher drain. Both make the **durable write the source of truth** and the Redis guard a mere fast-path optimization (the Redlock caveat, §12: the guard is never the correctness primitive). The reusable `Channel` seam factors in-app + email into two swappable implementations ([notification-ports.md](./contracts/notification-ports.md)).
- **Interactions**: the in-app "live badge" over Redis pub/sub stays **at-most-once** (a missed publish is cosmetic) because the unread count is always recomputable from the store and reconciled on SSE (re)connect (FR-034) — the outbox guarantees the *durable* inbox row + email, not the live nudge. Coalescing (FR-038) batches outbox entries within a window before dispatch. The `notify.email.<ws>` subject + email worker are **unchanged** — they become the transport the Dispatcher drives.
- **Alternatives considered**: (a) inline delivery + `SET NX` short-circuit (the earlier sketch) — rejected: loses a channel on a mid-handler crash. (b) ack only after all side-effects, no outbox — rejected: still loses the in-app/email work if the process dies after the DB commit but before the sends, and re-running the whole handler on redelivery re-does pref resolution and risks partial double-send with no per-channel state. (c) two-phase commit across Postgres + Redis + SMTP — rejected: no XA across these stores, and the outbox gives the same guarantee far more simply.

## 24. Sandbox runtime: isolated code/tool execution (hardened pod primary, microVM-upgradeable)

- **Decision**: Untrusted or model-**generated** code runs only inside an ephemeral, **credential-free, egress-locked sandbox** — never in the orchestrator process, never with ambient credentials. Phase 1 runs the **cheapest boundary that carries the invariants**: a **hardened container, no microVM** — **no new node group, no nested virt, no standing cost**. The *kind* implementing it is per-environment, because the targets differ in topology: `SANDBOX_KIND=docker` on local macOS (gVisor is Linux-only and Docker Desktop ships only `runc`) and on the **first DO deploy** (a single droplet running docker-compose — there is no Kubernetes API there); `k8s_pod` once k3s or EKS lands, which is the preferred posture since pod creation via an RBAC-scoped ServiceAccount is strictly less privilege than a runtime socket. On the Linux droplet, `SANDBOX_RUNTIME=runsc` (gVisor) is a free boundary upgrade and should be taken — it is a **one-flag change** (`--runtime=runsc`), not a re-platform. The tier is reached by a **thin `Sandbox` port** — the exact standalone-chokepoint + swappable-client shape as the LLM gateway (§21). Three workloads share it via versioned templates: `tmpl-crawl` (Crawl4AI headless Chromium), `tmpl-convert` (MarkItDown + parsers), and `tmpl-coderun` (Phase-2 code-gen). Stronger boundaries are the **same contract behind the same port**, swapped by config on **two orthogonal axes**: `SANDBOX_KIND` (`docker`|`k8s_pod`|`e2b_selfhost`|`e2b_cloud`) + `SANDBOX_URL` for *orchestration*, and `SANDBOX_RUNTIME` (`runc`|`runsc`) — **per-template overridable** — for the *isolation runtime*. Both invisible to callers. **Isolation strength is a deployment dial; the security contract is not.**
- **The control plane is privileged before the boundary is.** A sandbox tier fails hardest not at its isolation layer but at the thing that *creates* sandboxes. Two rules are therefore invariants (8–10 in [sandbox-runtime.md](./contracts/sandbox-runtime.md)), independent of `SANDBOX_KIND`: (i) **no component holds a host container-runtime socket** — it is host-equivalent privilege, a `:ro` mount does not help (read-only applies to the socket file, not the API), and the components handling untrusted channel input and model output are the worst possible holders; the K8s path creates pods through an **RBAC-scoped ServiceAccount** (`create`/`get`/`delete` on `pods` in one namespace, no `exec`, no cluster verbs), which is strictly less privilege. (ii) **no value from config, request, or model output reaches container-create arguments** — mounts, network mode, capabilities, `securityContext`, `runtimeClassName`, and seccomp profile come from a closed schema, and unvalidated-config-to-create is a recurring container-escape vector. A corollary falls out for free: because `files_in` stages from **S3 rather than host bind mounts**, forbidding bind mounts outright (invariant 9) *structurally* eliminates both mount-argument injection and the sibling-container host-path trap, rather than mitigating them.
- **Isolation ratchet (boundary bought where the risk is, not uniformly)**:
  - `tmpl-crawl` → **hardened pod**. Public `https` pages, Chromium keeps its own multi-process sandbox, HITL accept before indexing. Escape needs a renderer 0-day *plus* a kernel LPE, and lands on a credential-free pod with default-deny egress.
  - `tmpl-convert` → **gVisor (`runsc`)** when the path ships. Untrusted user-uploaded files through LibreOffice/pandoc/parsers is the genuinely higher-risk surface — worse CVE history than Chrome and no internal sandbox of its own. `runsc` needs no `/dev/kvm`, so it costs no infra.
  - `tmpl-coderun` → **gVisor + `max_runs=1`** (Phase 2), on the ordinary `k8s_pod` path. gVisor's designed purpose *is* untrusted code — Google runs multi-tenant customer code on it (Cloud Run, App Engine, GKE Sandbox) — and a Python transform script is a far better fit for it than Chromium. A microVM is **stronger but not required**; buy it only if the threat model changes (third-party-authored code, hostile tenants, a compliance rule naming hardware isolation). **Consequence: the KVM/`*.metal` pool may never need to exist.**
- **Two release-blocking invariants are preserved by keeping them *out* of the sandbox** (mirrors §21):
  - **Single ledger writer stays Go (SC-006).** Sandbox compute (`vcpu_seconds`/`wall_ms`/`egress_bytes`) is priced by a `Pricer` and emitted per-run as `billing.deduct.<ws>` (`operation_type=sandbox.*`); the Go billing worker remains the sole `credit_ledger` writer. The sandbox never writes the ledger.
  - **Access control stays at the data layer (SC-001).** A sandbox holds **no** provider key and **no** DB/Qdrant reachability; it sees only S3-staged, clearance-scoped files. Egress is **default-deny + allowlist proxy** (crawl gets exactly the `web_distill` SSRF allowlist; convert gets none), so generated code that needs AI/knowledge must call back through the LLM gateway / MCP chokepoint — it can't bypass them. Output re-enters the index only through the existing pipeline / HITL accept gate, so a poisoned page or crafted file can at worst influence a *draft a human reviews*.
- **Cost constraint (why microVMs are Phase 2, not Phase 1)**: Firecracker needs `/dev/kvm`. Standard EKS nodes (`t3.large`) and standard DO droplets **do not expose nested virtualization**, so a self-hosted fleet requires a dedicated **KVM/bare-metal pool** — on AWS that means `*.metal`, a **standing cost on the order of $3k/month** for the smallest x86 SKU. That is disproportionate to the Phase-1 crawl workload (member-initiated, low-volume, HITL-gated). The metal path stays fully specified and one flag away (`sandbox_enabled` in `deploy/eks/terraform/variables.tf`, **default `false`**), bought when `tmpl-coderun` ships. Two cost escapes exist if microVMs are needed sooner: **E2B Cloud** (usage-billed, no floor — but user files leave your infra under `tmpl-convert`) and **third-party bare metal** (Hetzner/OVH run the same Firecracker fleet at roughly 1/40th the AWS `*.metal` price, at the cost of an off-cluster network path). **This is why the port abstraction is load-bearing** — it is what lets Phase 1 ship on the cheap boundary without foreclosing the strong one.
- **Rationale**: crawl4ai (headless Chromium over attacker-pasted URLs) and MarkItDown (untrusted file parsers — a real parser-RCE surface) need isolation; the Phase-1 design peeled crawl onto its own pod for exactly this reason. Unifying crawl + convert + the future code-gen tool behind **one port** replaces N bespoke isolation stories with one — the same "delegate the commodity, keep only the invariants" logic as §21 — and makes boundary strength a per-workload, per-environment choice rather than an architectural commitment. Crucially, **six of the seven security invariants are enforced by the port, the policy plane, and the Go control plane rather than by the hypervisor** (no ambient credentials, access control, metering, HITL, resource caps, audit) and hold identically in a pod; the only property surrendered in Phase 1 is **kernel-escape resistance**, and only for crawl and convert.
- **Scalability**: ephemeral pooled sandboxes scale **independently of the orchestrator pods** (decoupling orchestration concurrency from execution compute). A cold Kubernetes pod (schedule → image pull → container start) is *seconds*, materially worse than a Firecracker boot — but the dominant terms are **pull** and **scheduling**, both fixable with **no freshness state**: pre-pulled images (a DaemonSet warmer or pinned `@sha256` + `IfNotPresent`) and a negative-priority `PriorityClass` placeholder holding node headroom. Those two land ~1–2 s and are bought **first**; a pod pool is a *last* resort, because it is a lease protocol whose four obligations (atomic claim, claimed-never-returns, failure-paths-destroy, provably-pristine members) all fail silently and turn `max_runs = 1` into `max_runs = N`. `tmpl-coderun` is never pooled. `max_runs_per_sandbox` plus a mandatory workspace-boundary recycle remain the isolation dial. Note the ~150 ms Firecracker figure is a *VM-boot* number and never described the crawl path: Chromium launch plus page navigation (~1–5 s) plus the downstream distill dominate at every backend, which is exactly why the cheap boundary is latency-adequate here. **Two-level autoscaling** (KEDA on JetStream lag → orchestrators; a second scaler → sandbox capacity) is deferred to **Phase 4** ([draft-plan.md — Phase 4](../draft-plan.md#phase-4-scalability-and-resilience-hardening)) — same seam-now/scale-later posture as §14.
- **Interactions**: the `ingestion.crawl.<ws>` NATS contract is unchanged — only its **consumer** changes from a bespoke Chromium image to a thin orchestrator over the `Sandbox` port (§the crawl role now runs from the `backend-python` image). `web_distill` (the SSRF-guarded fetch, [contracts/mcp-tools.md](./contracts/mcp-tools.md)) executes inside `tmpl-crawl`; the MarkItDown convert step executes inside `tmpl-convert`. Every run writes one `sandbox_run` audit row (the sandbox analogue of `agent_audit_log`, [data-model.md](./data-model.md)). The Phase-2 code-gen tool (`run_script`/`transform_files`) is an MCP Category-D action reusing the `human_gate` (fail-closed, no-spend-while-paused) — see [draft-plan.md — Decision 7](../draft-plan.md#decision-7--code-gen--file-manipulation-tools-run-in-a-sandbox-never-on-a-pod).
- **Alternatives considered**: (a) **Run crawl/convert in-process on the worker pods** — rejected: no isolation for attacker-influenceable input, and it puts a headless Chromium in the same process space as credentialed orchestration code. (b) **Self-hosted Firecracker microVMs as the Phase-1 primary** — rejected **on cost, not on merit**: it is the strongest boundary, but a ~$3k/month `*.metal` floor to isolate a low-volume, HITL-gated, public-URL crawl is disproportionate. Note this is no longer merely deferred: with `tmpl-coderun` landing on **gVisor** rather than a microVM, **no Phase-1 or Phase-2 workload requires `/dev/kvm`**, so the metal pool may never be provisioned at all. It stays one config flag away should the threat model change. (c) **Managed E2B Cloud as primary** — rejected as default: `tmpl-convert` would ship user-uploaded files to a vendor, and the crawl volume does not need it; kept as a config swap for dev/burst. (d) **gVisor (`runsc`) for everything in Phase 1** — rejected as the *default* only because it adds a node-runtime install for a boundary crawl does not need (and Chromium is gVisor's worst case: syscall-heavy, needs `--no-sandbox`); it is explicitly the planned per-template upgrade for `tmpl-convert`, which does need it. (d2) **Modelling gVisor as its own `SANDBOX_KIND` (`daytona`)** — rejected as a category error: gVisor is a runtime flag on existing orchestration (`--runtime=runsc` / `runtimeClassName: gvisor`), not a control plane, and folding it into the kind made the per-template ratchet inexpressible and made a one-flag change look like adopting a vendor. Daytona remains a legitimate *unadopted* peer of E2B if a managed control plane is ever wanted. (e) **A bespoke per-workload isolation image** (the earlier separate `crawl` image) — rejected: it does not generalize to convert/code-gen and forces N isolation stories instead of one port. (f) **Trusting an in-sandbox network path to providers/DB** — rejected: breaks SC-001/SC-006; the sandbox must round-trip through the existing chokepoints. (g) **A managed browser grid (Browserbase/Browserless) for crawl** — rejected: solves only crawl, leaves convert and code-gen without a home, and sends page content to a third party. (i) **[OpenSandbox](https://github.com/opensandbox-group/OpenSandbox) as the backend** — **ADOPTED as the default `SANDBOX_KIND` for `tmpl-coderun`; adoption is gated on the two open questions below.** An Apache-2.0 sandbox runtime for AI agents (verified 2026-08-02 via the GitHub API: 12.3k stars, 1.0k forks, Python, created 2025-12-17, pushed same day — active, but only ~8 months old). Per its README it supports **gVisor, Kata Containers, and Firecracker microVM** with both **Docker and Kubernetes** runtimes behind a FastAPI control plane — i.e. it is a productized form of this section's isolation ratchet and the `docker`/`k8s_pod` split, which is corroboration of the design rather than a reason to doubt it. **It would replace only the mechanical half.** The domain invariants stay in the `Sandbox` port and the Go control plane regardless of what executes the container: clearance-scoped S3 staging (3), metering to `billing.deduct` with Go as sole ledger writer (4, SC-006), the HITL gate (5), `sandbox_run` audit (7), versioned write-back (9), and the workspace-boundary recycle (12). So it enters as a `SANDBOX_KIND=opensandbox` behind the existing port, with callers and contract tests unchanged — and it would notably cover the unbuilt `k8s_pod` path (`deploy/eks/helm/` has no sandbox pool or RBAC manifests yet). **Why this is a coherent default rather than a leap:** `tmpl-coderun` was already gated on having a per-job substrate (k3s/EKS must land before agent code-gen ships), and OpenSandbox's Kubernetes runtime — built on `kubernetes-sigs/agent-sandbox` — *is* that substrate. So adopting it replaces work we would otherwise write, not a working system.

  **Two of the four questions are now partly answered from its README** (2026-08-02): per-sandbox **egress controls** are a documented feature (question 3, likely satisfied), and sandbox creation takes a `timeout` (partial for question 2). **Two remain open and are DECISIVE, so the default MUST NOT ship until both pass** — they are acceptance criteria on the implementation task, not follow-ups: **(1) Socket posture.** Its Docker runtime almost certainly needs a host container-runtime socket, which breaches **invariant 8** on plain compose — precisely the hazard `oneshot` was designed to avoid. Consequence: `opensandbox` is the default only where its **Kubernetes** runtime is available; `oneshot` remains the shipping fallback on compose. **(2) `max_runs = 1`.** Destroy-after-one-job is *unconfirmed*. A creation-time `timeout` is **not** the same guarantee — it bounds how long an instance lives, not how many jobs it serves. Reuse of an instance that has executed model-authored code is the single thing this template cannot tolerate, so absent an explicit never-reuse guarantee this backend is unusable for `tmpl-coderun` regardless of its other merits. **(3) Port exposure.** Its Docker runtime is reported to host-map random sandbox ports automatically (Jupyter/VNC-style access). That is new inbound exposure and contradicts a stated property of the DO stack — `docker-compose.prod.yml` asserts *"Only Caddy publishes ports"*. Sandboxes must reach the orchestrator on the internal network only, never via published host ports. **(5) Pool partitioning — SC-001.** General sandbox platforms pool warm instances for latency and key that pool by **template/image**, because that is all they know. Your boundary is `workspace_id`, a domain concept invisible to them. If it hands back a warm instance that last served workspace A while running workspace B's job, **SC-001 is breached silently** — nothing errors, nothing logs, the answer is simply built in an instance that previously touched another tenant's data. So: can its pool be partitioned by an opaque tenant key, or pooling disabled per template? If neither, either disable pooling entirely (forfeiting the latency benefit that motivates the platform) or it is unusable for multi-tenant work. **(6) Custom per-sandbox images.** It MUST boot our own `tmpl-*` images, not its stock runtimes. `tmpl-coderun`'s toolkit is a **tool contract** enumerated in the `run_script` description — a stock image breaks that silently, the description promising libraries the sandbox lacks. `tmpl-crawl` pins Playwright's Python package to the Chromium in its base image, a mismatch that fails at runtime rather than build time. And per-template caps, egress and `SANDBOX_RUNTIME` are ours. If it only boots curated images it is unusable regardless of everything else. **(4) RBAC narrowness** — `create`/`get`/`delete` on pods in one namespace, no `exec`, no cluster-scoped verbs — still needs reading; note a CRD/controller design typically implies a cluster-scoped operator, which is a broader grant than our own `k8s_pod` adapter would need. Weigh maturity too: 8 months is young for a **Tier-0** component on the ingest/agent critical path, though Apache-2.0 + self-hostable bounds the lock-in. (h) **A Docker-socket sibling-container orchestrator** (the common self-host agent-sandbox shape) — rejected as the EKS posture on privilege grounds, not convenience: the socket is host-equivalent, and there is no Docker socket on Kubernetes anyway, so every socket-shaped assumption would need rewriting at exactly the moment tenants are added. Retained only as `SANDBOX_KIND=docker` for local dev and single-host DO, under invariant 8's confinement rules.
